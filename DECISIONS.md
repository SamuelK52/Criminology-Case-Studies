# Decisions

Simplest reasonable choices made where the brief was unclear, and changes the owner asked for. Where this file and `docs/BRIEF.md` disagree, this file wins.

| # | Date | Decision | Why |
|---|---|---|---|
| 1 | 2026-11-06 | Project lives in `C:\Users\Samuel\dev\caselab`, outside OneDrive. | OneDrive syncing `node_modules` causes slow installs and `EPERM` file-lock errors. GitHub is the backup. |
| 2 | 2026-11-06 | Next.js 16.4 rather than 14. | The brief says "14+", and `create-next-app` installs 16. Cache Components is on, so request-time data (database, cookies) sits behind `<Suspense>` and `connection()`. |
| 3 | 2026-11-06 | `cases` has both `original_verdict` and `latest_outcome`. The prototype's single outcome text is seeded into `latest_outcome`, word for word, and `original_verdict` starts empty for lecturers to fill in. | The accuracy NFR says the two are always shown separately, but the seed has only one field, and case facts must not be rewritten. |
| 4 | 2026-11-06 | Sign-up offers Student, Study group and Lecturer. Lecturer is a *request* (`requested_role`) that the builder approves. Builder is set only by `npm run db:setup -- --builder email`. | Otherwise anyone could self-assign a role that edits the shared case bank. |
| 5 | 2026-11-06 | Signed-out visitors can read the **shared** case bank only. | The case facts are public, and the list must show before sign-in. Notes, resources, progress and class cases need sign-in. |
| 6 | 2026-11-06 | The prototype's 4 auto-made flashcards per case (`seedCards`) are stored as `derived` rows, rebuilt by a trigger when a case changes. Case 16's 7 EXTRA cards are `seed` rows (slots 1–7) and come first. | A lecturer's correction then reaches the cards, and students keep their spaced-repetition progress because card IDs don't change. |
| 7 | 2026-11-06 | The seed quiz is built at runtime from the case bank (as in the prototype). Nothing is stored. | It shuffles distractors from other cases each time. |
| 8 | 2026-11-06 | The PDPA guard is enforced in **both** the UI (`src/lib/pii.ts`) and the database (`has_pii()` check constraints). Boundaries are "not a digit", so a 17-digit number isn't flagged. A test checks that both agree. | The brief wants a clear message in the UI. The database stops a bypass. |
| 9 | 2026-11-06 | The AI rate limit (20 per user per rolling hour) is a Postgres function `ai_take_token()` that checks and records in one locked step. | No Redis needed, and it works with any number of app instances. |
| 10 | 2026-11-06 | A user's own case may not reuse a shared-bank case name, and user cases get codes `U1`, `U2`, … | Matches the prototype's duplicate check ("That case is already in the list.") and "U" ids. |
| 11 | 2026-11-06 | Lecturers can edit shared-bank cases (needed for FR-13: "Lecturer edits case 10") and cases in classes they teach, but can't change owner/code/class or delete cases they don't own. | Matches the role matrix: lecturers correct cases, but can't delete. |
| 12 | 2026-11-06 | Study-group members can save their own flashcard progress and quiz scores, but can't reset progress or write anything else. | The brief says they "flip flashcards, take quizzes and see their own progress", and the prototype locks Reset for them. |
| 13 | 2026-11-06 | DB tests use PGlite (Postgres in WebAssembly) and run as the real `caselab_app` role. | No Docker on this machine. PGlite runs the real migrations in real Postgres. |
| 14 | 2026-11-06 | Hosting is **Railway** instead of Vercel, at the owner's request. Railway project: `caselab` in "Goon Monster's Projects". **To do at first deploy (before 2026-12-01):** Railway is retiring `railway.json`, so once the app service exists, run `railway config migrate --variables unmanaged --apply`, then `railway config migrate cutover`, and commit `.railway/railway.ts`. `unmanaged` keeps secrets in the Railway dashboard, not in the repo. | The owner asked to link the project to their Railway account. |
| 15 | 2026-11-06 | **Plain PostgreSQL instead of Supabase**, at the owner's request (Railway Postgres in production). The schema is self-contained: own `users` and `sessions` tables, `current_user_id()` instead of Supabase's `auth.uid()`. The app talks to Postgres directly with `postgres` (postgres.js); there is no REST layer. | The owner asked for Postgres, not Supabase. |
| 16 | 2026-11-06 | **RLS without Supabase:** the app logs in as `caselab_app` (no superuser, no `BYPASSRLS`, doesn't own tables). Each request is one transaction that first sets `app.user_id`. The app builds its runtime URL from `DATABASE_URL`'s host and `APP_DB_PASSWORD`, so it never connects with the owner login. | It keeps the brief's rule: "enforce in the database with RLS, not only in the UI". **Trade-off:** with Supabase, the user id came from a signed JWT. Here the server sets it after checking the session cookie. RLS still catches bugs in app logic and UI bypasses, but it trusts the server code to set the right id. |
| 17 | 2026-11-06 | **Own email + password auth** (Milestone 2): scrypt password hashes (Node's built-in `crypto`, no native modules), random session tokens in an httpOnly, Secure, SameSite=Lax cookie, stored only as SHA-256 hashes, with a 30-day expiry. The app role can only reach credentials through `create_user`, `get_login`, `create_session`, `resolve_session` and `delete_session`. | It replaces Supabase Auth with the fewest moving parts, and nothing new is needed on Railway. |
| 18 | 2026-11-06 | Migrations are tracked in `schema_migrations` and applied once each by `scripts/db-setup.mjs`. Railway runs it as the **pre-deploy** command. The seed is idempotent and runs every time. | Deploys apply new migrations without anyone pasting SQL by hand. |
